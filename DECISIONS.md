# Decisions Register (append-only)

## [2026-07-06] Live-agent initiative — three-phase direction (LIVE.1 = Phase A)

**Context:** User wants LifeDash to shift from post-hoc pipeline (record → review later) to a live experience: an AI partner during recording, evolving toward Graphify-style structured knowledge (entities + typed edges + confidence tags, queryable by the agent).
**Decision:** Three sequential phases: A) Live Assistant (drawer with live transcript + on-demand agent chat with tools), B) ambient auto-triage feed (proactive suggestions, one-tap accept), C) knowledge-graph substrate (entity/edge tables in PGlite, extraction post-meeting first). LIVE.1 covers A only.
**Alternatives:** Building the knowledge graph first (rejected — most experimental, needs the live surface to be useful); one mega-plan for all three (rejected — exceeds 6-task limit, bundles unrelated smoke tests).
**Rationale:** Each phase validates the next; A reuses proven infra (streaming transcription, card-agent tool loop) so it's the cheapest slice that changes the product's feel.

## [2026-07-06] "Live Assistant" naming (not "Copilot")

**Context:** User asked whether "copilot" meant Microsoft Copilot — the term is now trademark-loaded and could read as a Microsoft integration.
**Decision:** User-facing name "Live Assistant"; internal naming `meeting_agent` (schema, service, IPC), task type `live_assistant`.
**Alternatives:** "Meeting Partner", "Live Intelligence", keeping "Copilot".
**Rationale:** Avoids brand confusion in a privacy-positioned product; "Live Assistant" is descriptive and pairs with the existing "Meeting Intelligence" naming.

## [2026-07-06] Local-first model policy for the Live Assistant

**Context:** Privacy is important but not a hard product line; user runs LM Studio with hardware for up to 14B models. Research (2026-07-06) tiered local models and ranked API privacy postures.
**Decision:** Live Assistant defaults to the user-configured local provider (LM Studio, Qwen3-14B class recommended) via the existing `resolveTaskModel` per-task routing — no new provider infra in Phase A. Cloud fallback stays user-chosen per task; future work may add Mistral/Groq and provider privacy badges.
**Alternatives:** Dual-model local tiering now (4B triage + 14B chat — deferred to Phase B where the triage loop exists); adding privacy-ranked cloud providers now (deferred, tracked in STATE.md pending items).
**Rationale:** Phase A is on-demand only, so one 14B model suffices; the per-task routing already expresses "local by default, escalate by choice". Research: complex KG relationship extraction (Phase C) exceeds 14B-class local models — revisit there.

## [2026-07-06] Live transcript state moves to recordingStore; drawer is a global portal

**Context:** The only `onTranscriptSegment` subscriber is MeetingsModern, so live segments are invisible on other views; child overlays hit a known stacking-context trap (standup picker precedent).
**Decision:** Single store-level transcript subscription (recordingStore) consumed by both MeetingsModern and the new LiveMeetingDrawer; drawer renders via `createPortal(document.body)` from AppLayout, only while recording.
**Alternatives:** Dedicated live-meeting route (rejected by user — leaves the Kanban); per-component IPC subscriptions (rejected — duplicate listeners, lost segments off-view).
**Rationale:** The user's core ask is working in Kanban while the meeting runs; one subscription avoids drift between surfaces.

## [2026-07-06] Live Mode pivot — recording becomes a full-screen takeover (supersedes the drawer decision)

**Context:** After LIVE.1 implementation, the user rejected the drawer positioning: "while the recording is happening nothing else should count at that moment... the live assistant should perform all tasks for me." The drawer optimized for multitasking the target user doesn't do mid-meeting.
**Decision:** LIVE.2 replaces the drawer with `LiveModeOverlay` — full-screen (FocusOverlay pattern), auto-enters on recording start, transcript spine + proposals feed + chat. Minimize collapses to the recording pill (deliberate escape hatch, not a hard lock; Esc minimizes, never stops). Drawer shell retired; its content components (transcript feed, chat) are recomposed inside the overlay. recordingStore transcript state carries over unchanged.
**Alternatives:** Hard navigation lock during recording (rejected — when the assistant can't do something, a locked UI turns a small gap into rage); keeping drawer as a middle state (rejected — three UI states is too many).
**Rationale:** For a meeting-intelligence-first product, the meeting is the main event; "LifeDash becomes the meeting" is the stronger product statement, and the expanded toolset makes leaving unnecessary rather than forbidden.

## [2026-07-06] Proactive proposals: propose → one-tap accept (not auto-execute)

**Context:** LIVE.2 pulls the ambient triage loop (old Phase B) forward. MEET-INTEL.1 precedent favored auto-execute+undo, but that was post-meeting batch output of a proven extraction; live triage runs a local 14B on noisy in-flight transcript.
**Decision:** Detected items (action_item/decision/question) land in `live_suggestions` as chips with one-tap Accept/Dismiss. Accepting an action_item creates the card through the live-assistant rails; decisions/questions become brief context. Auto-execute may graduate later as a settings flip. Accepted live items are suppressed from the post-meeting extractor to prevent duplicate cards.
**Alternatives:** Auto-execute + undo (rejected for v1 — noisy transcript + unproven local-model precision could spray the Inbox); hybrid by confidence (rejected — local-model confidence is poorly calibrated; two code paths for v1).
**Rationale:** Trust graduates with evidence; the propose model costs one tap and protects the Inbox while 14B precision is unproven.

## [2026-07-06] One local model serves chat + triage, chat priority (task type `live_triage`)

**Context:** User hardware runs one ~14B model in LM Studio alongside whisper.cpp; LM Studio serializes concurrent requests to a loaded model.
**Decision:** `live_triage` is a distinct task type whose model resolution falls back to `live_assistant`'s — same model by default, splittable in Settings later. Triage is cadence-gated (≥4 new segments ≈ 40s), skips (never queues) when a chat stream is in flight, caps 3 proposals per run, and degrades to "fewer proposals" on JSON failure (retry once, then skip — never throw into the recording pipeline).
**Alternatives:** Loading a second small model (Qwen3-4B) for triage now (rejected — VRAM contention with 14B + whisper unverified; the task-type split keeps this a settings change later); fixed timer instead of segment-count cadence (rejected — ties triage to wall-clock instead of actual speech volume).
**Rationale:** Chat is the user-facing interaction and must stay responsive; triage is background work that tolerates postponement.

## [2026-07-06] LIVE.3 scope + method — field-test fixes and project-proposal triage; Fable plans, Opus ultracode executes

**Context:** First real-meeting test of Live Mode (LIVE.2, uncommitted) surfaced three things: (A) the overlay chat is not clickable (static root-cause hunt across handlers, z-stack, scanlines, ConfirmDialog, the z-[100] pointer-events-none HUD beam, and the 36px TitleBar drag strip found no covering element); (B) high GPU during recording; (C) the user does not want to chat mid-meeting, so the assistant should be able to create a project itself from the conversation.
**Decision:** Bundle all three into a LIVE.3 plan (6 tasks). (1) Clickability fix is EMPIRICAL-FIRST — reproduce via `document.elementsFromPoint` in the running app before touching code; when the fix must be produced headless, apply the justified defensive union (raise the overlay above app chrome z-index + `isolation: isolate` + `WebkitAppRegion:'no-drag'` on the overlay root) and confirm via the user's manual smoke test. (2) GPU is split into inherent-vs-fixable: the dominant cost (whisper.cpp GPU + the 14B LM Studio model + triage cadence) is INHERENT to the 100%-local design and explicitly out of scope; the fixable renderer waste is AudioLevelMeter's never-settling 60fps canvas rAF (Math.random per frame) plus a second meter instance running behind the overlay — park the loop at silence, cap ~30fps, render only one meter; plus a main-process lever: triage yields to in-flight transcription via a one-way injected busy-probe (no new import cycle). (3) Project creation uses the propose→one-tap-accept model, NEVER auto-create: a new `live_suggestions` type `'project'` (+ `acceptedProjectId`, migration 0038); triage proposes at most one "Create project: {name}" chip when the meeting is unlinked; accept creates the project and links the meeting (reusing meetingService.updateMeeting, which already auto-pushes pending action items), rerouting future accepted items into it; a secondary `createProject` agent tool covers the typed-chat path.
**Method:** Planned with Fable (claude-fable-5); executed with Opus 4.8 + ultracode (multi-agent Workflow), per explicit user direction. Tasks run in dependency order (clickability + the two perf tasks are independent; schema 0038 → project rails → triage/UI feature slice must be sequential). Runtime acceptance rests on the user's manual smoke test per project convention.
**Alternatives:** Auto-create + link projects silently (rejected — a 14B on noisy transcript could spawn spurious projects, harder to undo than a card); shotgun z-index changes for the click bug (rejected — guess-fix without evidence); claiming the GPU is "fixable" wholesale (rejected — dishonest; the dominant cost is inherent local inference); post-meeting-only project prompt (rejected — doesn't solve the mid-meeting ask).
**Rationale:** The click bug blocks all other Live Mode verification, so it goes first and must be evidence-driven. Honesty about inherent GPU protects trust while still removing the real renderer waste. The propose→accept project chip extends the already-proven LIVE.2 model with the least new risk and directly answers "I can't chat while people are talking to me."

## [2026-07-07] V3.1 execution — two coexisting boards resolved with an `active` guard; ultracode adversarial review folded into the plan

**Context:** /nexus-execute V3.1 (6 tasks) shipped the session-centric rebuild: 3-entry nav, /session/:id pages (MeetingDetailModal deleted), a `data:changed` broadcast + debounced refetch, EmbeddedBoard extracted from BoardPageModern, the Transcript|Board|Brain live canvas, an activity feed, and query-time FTS. A 22-agent adversarial review (6 dimensions × 2-lens verify) over the full diff found 7 real, V3.1-introduced bugs that 766 green tests + tsc + lint all missed.
**Decision:** (1) **Board coexistence model = an `active` guard on `useBoardController`.** Because `LiveModeOverlay` is a `document.body` portal that layers over the still-mounted route, an overlay-owned EmbeddedBoard and a route-owned EmbeddedBoard can be mounted at once, both driving the single global `boardStore` and both registering document-scoped drag monitors → wrong-board display + duplicate drag side-effects. Resolved by making a covered route board inert: `active={!(isRecording && !liveModeMinimized)}` on route boards (BoardPageModern + SessionWorkspace Board tab); the overlay board stays `active`. An inert controller registers no monitors and does not `loadBoard` (no stomp), and self-heals (reloads its projectId) when `active` flips back true. The overlay-visible predicate `isRecording && !liveModeMinimized` is the canonical "is the live takeover covering the route" signal — reuse it for any future surface that coexists with the overlay. (2) **`useBoardLiveSync` refetch re-reads the current board at timer-fire** (not the id captured at event time) so navigation within the 300ms debounce never resurrects the old board. (3) **The agent `moveCard` tool now broadcasts** — every meeting-agent tool write path hits `notifyDataChanged`. (4) **Per-card Reject/Keep for auto-pushed cards lives on the session Board tab** (real KanbanCardModern cards), NOT reimplemented on the page — there is no "list a meeting's cards" IPC and building one to fake it was rejected as fabrication.
**Alternatives:** Per-project keying of `boardStore` (rejected — a larger, riskier re-architecture than the contained `active` guard; the guard fully addresses both the stomp and the duplicate-monitor findings); scoping drag monitors by `canMonitor` board-id (rejected — the `active` guard is simpler and also fixes the load-stomp, which a canMonitor scope would not); deferring the board-concurrency findings to ISSUES.md (rejected under ultracode — they degrade the headline "watch the assistant work" flow, and the fix proved low-risk with a regression suite).
**Rationale:** The overlay-over-route topology is intrinsic to the full-screen live takeover, so the coexistence had to be modelled explicitly rather than assumed away; the `active` guard is invisible to users (an inert board is always fully covered) yet deterministically prevents the store stomp and duplicate side-effects. Running the adversarial review before the user's smoke test caught defects (infinite-spinner dead-end, wrong-board race, onboarding tour walking new users through deleted sections) that no automated gate surfaced — validating the ultracode "verify before you trust green" posture on a large, MEDIUM-confidence diff.

## [2026-07-07] Brain live growth: refetch-and-diff, not event→insert (V3.2 promotion revalidation)

**Context:** Promoting PLAN-V3.2 into PLAN.md. The parked Task 4 mapped renderer events to targeted mind-map inserts ("new card → insert under its column node"), with dedupe + a >25-delta refetch fallback. Revalidation against the shipped V3.1 code showed the premise is false: the `data:changed` payload (dataChangeNotifier.ts) is `{ scope: 'cards'|'columns'|'projects', projectId? }` — scope-level by design, no entity identity — so the renderer cannot know WHAT changed, only that something did.
**Decision:** brainStore refetches the active scope's full tree (300ms trailing debounce on `data:changed`, mirroring useBoardLiveSync) and DIFFS node-id sets (ids stable, derived from entity type + id) to find entering nodes — those drive entrance animations, collapsed-ancestor chevron badges, and the Brain canvas badge. Decision/question chip accepts, which never emit `data:changed` (no card mutation), trigger the same refresh through the liveSuggestionsStore accept() success seam — the exact hook that already feeds activityFeedStore. The parked dedupe/threshold machinery is deleted.
**Alternatives:** Enriching `data:changed` payloads with entity ids + parent paths so targeted inserts work (rejected — adds main-process surface and a second consumer contract to keep honest at every mutation site, for marginal gain when the full tree is hundreds-to-low-thousands of nodes over one IPC); keeping event→insert only for the suggestion-accept path where rich data exists (rejected — two growth code paths that must agree beats nothing; one path that cannot drift wins).
**Rationale:** Refetch-and-diff is one code path for every trigger, idempotent under the broadcaster's known double-fires (they collapse into a single debounced refetch; an unchanged id-set animates nothing), and strictly simpler than what it replaces — the scope-level broadcast was V3.1's deliberate "impossible to forget at new mutation sites" design, and this keeps V3.2 a pure consumer of it.

## [2026-07-08] V3.3.5 execution — parallel-batch contract-freeze; merge-not-replace refine seed (data-loss fix); provider-native web search (supported); Gemini as frontier provider

**Context:** /nexus-execute V3.3.5 (6 tasks, 989→1126 tests). Executed as a parallel batch and hardened by a 23-agent adversarial review. Several forks and one serious defect were resolved during execution.
**Decision:**
(1) **Deep-creation drafts MERGE over the existing profile on refine; they never replace it.** `TwinWizard.seedFromPanelDraft` seeds the shared editable review from a deep/history/web `Partial<TwinProfileSections>` draft via `seedSuppliedSections(prev, draft)`, which overrides ONLY the sections the draft actually supplies (`'key' in draft`) and preserves every section it omits. This closes a HIGH-severity data-loss bug the adversarial review found (3 dimensions, both verify lenses): because `twinProfileService.updateProfileSection` is a per-section jsonb REPLACE and the wizard's `writeAllSections` writes all 8 sections on save, the previous "reseed drafts from the panel draft alone" wiped stored `identity`/`preferences` (which history mining structurally excludes) with `{}`. Guarded by `TwinWizard.refineMerge.test.tsx` (failing-before/passing-after). `brief` remains special-cased.
(2) **The deep interview lives in a NEW `twinDeepInterviewService` (interviewNext/interviewSynthesize), not `twinInterviewService`** — keeps the V3.3 `draftSection` seam untouched and gives the frozen IPC a stable delegate. Transport is invoke-per-turn (extends the V3.3 invoke-not-streaming decision): each turn is a small request→JSON via `taskType:'twin_interview'`, validate-retry-skip, hard 8-question cap.
(3) **Web research uses provider-native server-side search ONLY, and the installed stack SUPPORTS it** — the Task-4 preflight (reading node_modules types, not memory) confirmed `ai@6` + `@ai-sdk/{anthropic,openai,google}` expose `webSearch_20250305`/`webSearch`/`googleSearch` with citations on `steps[].sources`. ## [2026-08-01] LOCAL-RT.1 Task 2 — `ensureRunning(role, modelId?)` is the final contract; no `--device`; explicit chat context; per-spawn API key

**Context:** Task 2 implemented the sidecar supervisor and the `builtin` provider case. Three decisions had to be made on purpose rather than inherited: (a) the frozen `ensureRunning(): Promise<{baseUrl}>` signature cannot express the two-process topology Task 1 proved necessary; (b) the spike pinned `--device Vulkan0` as a convenience and flagged that shipping it would be wrong; (c) the spike measured 10.9GB VRAM for ~5.3GB of weights and could not attribute it precisely. All three were resolved with fresh measurements against the pinned b10219 binary on the dev machine.
**Decision:** (1) **Public contract, final — Tasks 4/5/6 code against this:** `ensureRunning(role: 'chat'|'embedding', modelId?: string): Promise<{ baseUrl; modelId; backend; apiKey }>`, `stop(role?): Promise<void>` (omit role = all), `status(): LlamaRuntimeStatus` (`running, backend, binaryAvailable, loadedModels, chat, embedding, idleStopMinutes`), `touch(role)`, plus pure helpers `isBinaryAvailable()`, `getModelsDir()`, `listAvailableModels()`, `getBinaryDir()`, `binaryCandidates()`. The endpoint carries `modelId` (the resolved model, equal to the process's `--alias`) and `apiKey` because both are per-spawn facts the caller cannot know; `baseUrl` remains never-persisted. Roles are independently lazy; one process per role, so requesting a different model for a role stops the running one. (2) **No `--device` flag is shipped.** Measured on the dev machine (NVIDIA RTX 4070 SUPER as `Vulkan0`, AMD iGPU as `Vulkan1` reporting 46GB "free" vs the dGPU's 11GB): with no `--device`, b10219's `common_params_fit_impl` logged `llama_prepare_model_devices: using device Vulkan0 (NVIDIA GeForce RTX 4070 SUPER)` and assigned all 25 layers there — it picks a device itself and does not split onto the iGPU. Hardcoding `Vulkan0` would pin users whose device 0 is a weak iGPU to that iGPU. (3) **Chat gets explicit `--ctx-size 16384 --parallel 1 --fit-target 2048`.** Root cause of the spike's VRAM number found: b10219 ships `-fit on` by default, which grows _unset_ params until only ~1GiB of device memory remains (`common_params_fit_impl: will leave 10903 >= 1024 MiB of free device memory`) — that is why it chose `n_slots=4, n_ctx_slot=131072`. Setting ctx and slots explicitly bounds the KV cache (live run logged `n_slots = 1, n_ctx_slot = 16384`), and raising the fit margin to 2048MiB keeps headroom for whisper, which shares the GPU. The embedding process deliberately keeps llama-server's own slot/context defaults (its footprint is ~0.8GB) and adds only `--ubatch-size 2048`: without it llama-server logs `embeddings enabled with n_batch (2048) > n_ubatch (512) / setting n_batch = n_ubatch = 512` and rejects inputs over 512 tokens — with it, a 1,764-token input embedded successfully at 768 dims. (4) **Every spawn gets a random `--api-key` plus `--cors-origins localhost`.** llama-server itself warns `CORS is set to allow all origins ('*') and no API key is set / this can be a security risk`; verified that an unauthenticated request returns HTTP 401 while `/health` stays reachable. The AI SDK's existing `Authorization: Bearer` path carries it, so this costs no new code. (5) **Crash restart is lazy, not eager:** a crashed sidecar stays dead until the next routed request, which then applies 1s/2s/4s backoff and refuses after 3 restarts in a 5-minute window. (6) `builtin` reaches the AI SDK through `createOpenAI({ fetch })` — a custom fetch resolves the live origin, injects the bearer token, lazily starts the right role, retargets the `default` sentinel model id to the real one, and counts streamed chunks as activity so idle auto-stop cannot kill a live generation.
**Alternatives:** Keeping the literal single-URL `ensureRunning()` and adding a second function per role (rejected — two entry points for one concern, and Tasks 4/5/6 would have to branch); hardcoding `--device Vulkan0` as the spike did (rejected — measured to be unnecessary and actively harmful on iGPU-first machines); exposing device choice as a v1 setting (deferred — llama.cpp's own fitting was observed to be correct here, so a setting would be UI for a problem not yet seen; Task 4 may add it if a user reports otherwise); calling `ensureRunning()` at each of the many AI call sites instead of inside a custom fetch (rejected — it would touch every feature service and could not resolve the port at request time); eager crash restart (rejected — a restart with no pending request re-reserves GPU memory a user may not want, and lazy restart gives the same user-visible resilience); a `parallel 1` slot cap on the embedding process too (rejected — measured tiny footprint, and the live run showed llama-server usefully spreading a 2-input batch across slots 2 and 3).
**Rationale:** Every flag shipped is verified against `llama-server --help` for b10219 _and_ by running the binary; nothing is inherited from the spike unexamined. The `-fit`-on-by-default discovery converts the spike's "VRAM hazard, cause unattributed" into a precise, fixed cause with a bounded fix, which is what protects transcription from being starved. Live end-to-end evidence (`ai-provider.builtin.live.test.ts`, skipped by default, `BUILTIN_LIVE=1` to run): 768-dim embeddings with real model provenance from the embedding process while the chat process was provably not started, `testConnection('builtin')` succeeding, and a streamed chat completing with `finishReason: 'stop'` — passing against both the CPU and Vulkan builds, with all sidecar processes confirmed gone afterwards via `tasklist`.

(2) **URLs are pinned to the repo's 40-hex commit sha (`/resolve/<sha>/`), not `/resolve/main/`.** A `main` URL lets an uploader replace the bytes behind a recorded hash, which would turn every future download into a checksum failure with no recourse; a pinned revision cannot drift. Asserted by test. (3) **Google's own Gemma GGUF repos were dropped: they are `gated: manual` and return HTTP 401 to anonymous downloads** (verified with a real request to `google/gemma-3-12b-it-qat-q4_0-gguf`). Replaced with the ungated `ggml-org/*` conversions (the llama.cpp org's own). **Ministral-8B was dropped** — `bartowski/Ministral-8B-Instruct-2410-GGUF` is licensed `other` (Mistral Research License, non-commercial), unfit to recommend in a catalog whose license field drives user policy decisions. (4) **`toolCalling` records what the shipped GGUF can actually do, not what the upstream model claims.** `Mistral-7B-Instruct-v0.3`'s official card advertises function calling, but the chat template embedded in the GGUF has no tools section, so through llama.cpp `--jinja` it cannot tool-call: recorded `false` with a note explaining the divergence. Same for Gemma-3 and Phi-4. (5) **The remote catalog path was verified, not guessed: `Lab-51/lifedash` is PUBLIC** — `raw.githubusercontent.com/Lab-51/lifedash/main/package.json` returns 200 and the repo API returns 200. `catalog/models.json` currently 404s only because the file is new and uncommitted; the remote path is wired and correct, and until the file is pushed the service silently degrades to bundled, which is the designed behavior. (6) **Verification re-reads the whole `.part` at completion instead of persisting incremental hash state.** Node's crypto hash state cannot survive a process exit, so a resumed download could never be verified from a streaming hash; a full re-read is ~20-60s on a 9GB file and is always correct. This is why `verifying` is a distinct user-visible state. (7) **Partial-file cleanup deletes exactly two named paths** (`<name>.gguf.part`, `<name>.gguf.part.json`), each `lstat`-checked as a regular file first — never a directory, never a glob, never recursive (2026-07-21 process-incident lesson). A `.part` whose sidecar names a different URL/hash is discarded rather than resumed onto, so a superseded catalog entry can never splice two files together. `deleteModelFile` resolves through `path.basename` and asserts the parent is exactly the models dir. (8) **Sync safety:** a failed, timed-out, malformed **or empty** remote catalog is treated as a bad response and falls back to cache → bundled; an empty `models` array is explicitly never interpreted as "these models were removed", and no code path in the catalog service deletes a model file. (9) **Custom GGUFs:** registered with `vendor:'custom'`, origin/license `'unknown'`, and `contextLength: 0` / `minRamGB: 0` / `parameters: 'unknown'` meaning "unknown" rather than a guessed number. A local path is **hard-linked** into the models dir (instant, no extra disk) with a copy fallback across volumes. Registration **rejects a filename whose `/embed/i` match contradicts the declared role**, because llamaRuntimeConfig would otherwise silently serve it under the wrong role. (10) **Catalog cache and custom-model registry live inside `getModelsDir()`** (`catalog-cache.json`, `custom-models.json`), reusing Task 2's single `LIFEDASH_LLAMA_MODELS_DIR` override for tests instead of introducing a second env var; `listAvailableModels()` filters `.gguf` so they are invisible to the runtime.
**Alternatives:** Hand-writing the catalog from model knowledge (rejected outright — the single worst outcome named in the story; a wrong hash is indistinguishable from a right one in review); `resolve/main/` URLs (rejected — mutable bytes behind an immutable hash); keeping Google's official QAT GGUFs and asking users to log in to Hugging Face (rejected — an auth wall inside a "download a model" button, for a product whose whole point is removing setup friction); including Ministral-8B for FR coverage at 8B (rejected on license; `Mistral-7B-Instruct-v0.3`, Apache-2.0, was used for the 16GB FR slot instead); trusting upstream model cards for `toolCalling` (rejected — the GGUF's own template is what llama.cpp actually executes); persisting incremental sha256 state across restarts (not possible with `node:crypto`); a separate `LIFEDASH_LOCAL_CATALOG_DIR` env var (rejected — one override is enough); storing custom models in the settings table (rejected — would pull the DB into a service that must not touch it).
**Rationale:** The catalog is the one artifact in this phase where being _confidently wrong_ is worse than being _incomplete_, so every field traces to a response captured this session and the shipped file is machine-generated from that capture. The resume path was proven the same way rather than argued: phase 1 of `modelDownloadService.live.test.ts` downloaded the real 333,590,944-byte EmbeddingGemma entry from the real CDN and the OS process was **force-killed** at 84,706,056 bytes; a **separate** process then resumed with `Range: bytes=84706056-`, received HTTP 206 with `content-range: bytes 84706056-333590943/333590944` and `content-length: 248884888` (i.e. only the remainder crossed the wire), and finished with a sha256 equal to the catalog's — independently re-confirmed with `sha256sum`. That single run simultaneously proves Range resume across a real restart _and_ that the shipped URL/size/sha256 for that entry are correct end-to-end. **No deviation from the frozen `localModels.ts` contract** — the frozen block is implemented verbatim; everything added (`ResolvedCatalog`, `CatalogModelStatus`, `LocalModelDownloadProgress`, `LocalModelsView`, `RegisterCustomModelInput`, and the pure `fileNameForUrl`/`runtimeModelIdForUrl`/`inferredRoleForFileName` helpers) is additive surface Tasks 4/5 can rely on. The filename↔role derivation lives in that shared file rather than being re-derived per call site, and a test asserts `/embed/i` matches a filename **iff** the model's role is `embedding` across the whole bundled catalog — the single silent-breakage trap the story flagged.

## [2026-08-02] LOCAL-RT.1 Task 6 — the shipped unit is a directory, not an executable; the sha256 gate is the build step, not a comment

**Context:** Staging the pinned llama.cpp binaries into a packaged build, with an MIT notice and docs, without a release ceremony (package.json stays 2.6.0). Three facts shaped every choice: the release zips are not a single `.exe` (`llama-server.exe` is a 9 KB launcher over `llama-server-impl.dll` plus ~30 sibling DLLs including the 52 MB Vulkan backend and 14 `ggml-cpu-<arch>` micro-arch variants ggml picks between at runtime); the integrity fuse is on, so binaries can only go in `extraResource`; and both CI workflows invoke `npx electron-forge make` directly, so npm lifecycle hooks would never fire.
**Decision:** (1) **`scripts/fetch-llama-server.js` is the only path binaries enter the build.** It downloads the pinned tag `b10219` for the host platform, verifies size + sha256 against constants recorded in the script, caches archives under `.cache/llama-bin/`, and stages `resources/llama/<backend>/` — the exact layout Task 2's `llamaRuntimeConfig.getBinaryDir()` resolves, so no retrofit was needed. A cache entry that fails verification is deleted and re-fetched; a fresh download that fails verification is deleted and the build stops. Nothing unverified is ever staged. (2) **Wired as a forge `prePackage` hook**, not an npm `prepackage` script — `electron-forge package`/`make` cover local, CI and `make:dist` alike, and the hook is a ~80 ms no-op once the cache is warm. (3) **The staged unit is `llama-server` + its complete `.dll`/`.dylib` set, minus every other CLI tool.** All libraries are kept (ggml loads its CPU and GPU backends dynamically — a subset is a runtime failure waiting for a specific CPU); the extra executables are dropped, which also keeps `ggml-rpc-server.exe`, a network daemon, out of a privacy-first app. Verified by running the pruned set: `--version` succeeds and `--list-devices` enumerates both Vulkan GPUs. (4) **macOS = arm64 only, sha256 `b54af3c25a3ded15fc0f7a5a0898a65f1a9beb63981a93e0ae93f648811fb960`, computed locally and matched against the release API's digest** — `.github/workflows/release.yml` builds exactly one macOS arch (`macos-latest` → `mac-arm64`), so pinning a second one would ship an asset nothing consumes. Its `libfoo.dylib → libfoo.0.dylib → libfoo.0.18.0.dylib` chains are recreated as symlinks. (5) **`THIRD_PARTY_NOTICES.md` at the repo root _and_ in `extraResource`** — MIT requires the notice to travel with the binaries, and a repo file does not ship in an installer. It covers whisper.node too, whose binaries were already being redistributed without a notice. (6) **No new npm dependency:** bsdtar (`tar`) ships with Windows 10+ and macOS and reads both `.zip` and `.tar.gz` while preserving symlinks and exec bits.
**Alternatives:** `extract-zip`/`yauzl` (present transitively, rejected — a build-critical step should not rest on a transitive dep, and neither reads `.tar.gz`); npm `prepackage` lifecycle (rejected — both CI workflows bypass npm scripts); shipping the archives whole (rejected — bundles an RPC server daemon and ~6 MB of unused tools per variant); shipping only the Vulkan build, which already contains the CPU backends (rejected — contradicts the Task 1 decision and Task 2's `['vulkan','cpu']` chain); dereferencing the macOS symlink chains for safety (rejected — Electron's own `.app` ships symlinked frameworks, so preservation through packager/DMG/ZIP is already proven by the shipping product); committing the binaries (rejected — 137 MB); `fs.rmSync(recursive)` for staging cleanup (rejected outright — the 2026-07-21 incident where a recursive delete followed a junction; cleanup instead unlinks entries one by one, refuses symlinked and non-directory roots, refuses depth > 2, and refuses any path outside the project root).
**Rationale:** Every claim was measured, not assumed. Cache proof: first run 2.0 s (downloads), second run **0.08 s** with `cache HIT … no download` and `already staged … skipped`. Supply-chain proof: flipping a single byte in a cached archive (size unchanged, so only the hash can catch it) produced `cache entry rejected … sha256 ce9fbe47… != pinned 5f3fc78e…` followed by a clean re-download. Packaging proof: `npm run package` → 63 files / 143,216,438 bytes under `resources/llama/`, `verify-package.js` 28/28 PASS including the new library-set, CPU-backend-count and `provenance.json` tag assertions. Optionality proof: the packaged app booted on a throwaway `--user-data-dir` profile with **zero `llama-server` processes** and not one mention of llama/spawn/sidecar in the boot log — presence is not execution. Installer proof: `installer/lifedash.iss` needed **no change** (its `recursesubdirs` glob compressed `resources\llama\**` on its own, visible in the ISCC log) and the payload grew **209.9 MB → 230.2 MB, +20.3 MB** — well under the ~50 MB estimate, because lzma2/ultra64 solid compression beats the release zips' own deflate. Baselines held exactly: 1839 passed / 8 skipped / 0 failed (151 files), `tsc --noEmit` clean, eslint 377 warnings / 0 errors. **Not verifiable on Windows and marked for CI:** the macOS `metal` staging path — the arm64 asset was downloaded, hashed and its layout inspected, but extraction, symlink recreation, exec-bit preservation and Gatekeeper behaviour can only be exercised by the macOS runner.
